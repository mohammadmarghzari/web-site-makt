# MAKT — فروشگاه اکشن‌فیگور

فروشگاه تک‌برند اکشن‌فیگورهای کلکسیونی مقیاس ۱/۱۲. فارسی، راست‌چین، با سه «پردهٔ» تمام‌صفحه که با اسکرول به‌صورت سینمایی و **کاملاً دوطرفه** به هم تبدیل می‌شوند.

سایت یک **خروجی کاملاً ثابت** است و روی GitHub Pages منتشر می‌شود — بدون سرور، بدون هزینه، بدون کارت بانکی.

**همین حالا و بدون هیچ تنظیماتی کار می‌کند** و با دادهٔ نمونه بالا می‌آید. با وصل‌کردن Supabase، محصولات واقعی و پنل مدیریت و ثبت سفارش فعال می‌شوند.

```bash

npm run dev        # http://localhost:3000
npm run build      # خروجی ثابت در پوشهٔ out/
npm run typecheck  # بررسی تایپ‌ها
```

نیازمندی: Node نسخهٔ ۲۰ یا بالاتر.

## ۱) گرفتن لینک سایت

### فعال‌کردن (یک بار، از موبایل)

۱. در گیت‌هاب وارد مخزن شوید → `Settings` → از ستون کنار، `Pages`

۲. زیر **Build and deployment**، بخش **Source** را روی **GitHub Actions**
   بگذارید (نه «Deploy from a branch»)

۳. تمام. به تب `Actions` بروید؛ اگر اجرایی در جریان نبود، روی
   «انتشار روی GitHub Pages» بزنید و `Run workflow`.

بعد از حدود دو دقیقه لینک آماده است:

```
https://mohammadmarghzari.github.io/web-site-makt/
```

**از این به بعد هر پوش روی `main` خودکار منتشر می‌شود.**

### دامنهٔ اختصاصی (اختیاری)

`Settings` → `Pages` → `Custom domain`. بعد در `next.config.ts` مقدار
`basePath` را خالی کنید — دامنهٔ اختصاصی از ریشه سرو می‌شود نه از زیرشاخه.

## ۲) وصل‌کردن دیتابیس

بدون این مرحله سایت کار می‌کند، ولی محصولات ثابت‌اند، پنل مدیریت غیرفعال است و
سفارش ثبت نمی‌شود.

**۱.** در `supabase.com` یک پروژهٔ رایگان بسازید (کارت بانکی نمی‌خواهد).

**۲.** در داشبورد → `SQL Editor` → دو فایل زیر را **به همین ترتیب** پیست و
`Run` کنید:

| فایل | چه می‌سازد |
|---|---|
| `supabase/migrations/0001_init.sql` | جدول‌ها، سیاست‌های امنیتی، باکت فایل‌ها، ۶ محصول اولیه |
| `supabase/migrations/0002_place_order.sql` | تابع ثبت سفارش |

هر دو idempotent‌اند: اجرای دوباره خطا نمی‌دهد و داده را پاک نمی‌کند.

**۳.** در داشبورد → `Project Settings` → `API` دو مقدار را بردارید. در گیت‌هاب →
`Settings` → `Secrets and variables` → `Actions` → `New repository secret`:

| نام Secret | مقدار |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon / public key |

> کلید `anon` عمومی است و طبق طراحی داخل مرورگر دیده می‌شود؛ چیزی که از داده
> محافظت می‌کند RLS است، نه مخفی‌بودن این کلید. کلید `service_role` را
> **هرگز** اینجا نگذارید — در یک سایت ثابت هیچ جای امنی برایش وجود ندارد و
> اصلاً به آن نیازی نیست.

**۴.** در تب `Actions` یک بار `Run workflow` بزنید تا سایت با دیتابیس بیلد شود.

**۵.** به `/admin/` بروید، «اولین بار است؟ حساب بسازید» را بزنید و ثبت‌نام کنید.

**۶.** برگردید به SQL Editor و این خط را با ایمیل خودتان اجرا کنید:

```sql
update public.profiles set role = 'admin' where email = 'you@example.com';
```

ثبت‌نام به‌تنهایی دسترسی مدیر نمی‌دهد — این خط می‌دهد. پس لو‌رفتن نشانی
`/admin` خطری ندارد.

**۷.** یک بار خارج و دوباره وارد شوید. پنل فعال است.

## پنل مدیریت

نشانی: `/admin/` — راست‌چین، با همان پالت سایت، و **کاملاً قابل استفاده از موبایل**.

- **محصولات** — جست‌وجو، فیلتر وضعیت، افزودن و ویرایش، آپلود چند عکس، جابه‌جایی ترتیب، و حذف با تایپ نام محصول به‌عنوان تأیید.
- **پرده‌ها** — آپلود دسته‌ای فریم‌های دنبالهٔ عکس، آپلود پوستر، ویرایش خط‌به‌خط تیتر، اسلایدر شدت تیرگی، و **پیش‌نمایش زنده** با همان موتور رندر واقعی.
- **سفارش‌ها** — مشخصات مشتری، اقلام و مبلغ.
- **تنظیمات** — نام برند، لوگو، شبکه‌های اجتماعی، هزینهٔ ارسال.

### امنیت پنل روی سایت ثابت

اینجا سروری وجود ندارد که جلوی کسی را بگیرد، و **لازم هم نیست**. محافظت واقعی
در خود دیتابیس است: هر جدول سیاست RLS دارد که نوشتن را فقط برای نقش `admin`
مجاز می‌کند. کسی که کد صفحه را دور بزند، در بهترین حالت به یک فرم خالی می‌رسد —
Postgres هر دستورش را رد می‌کند.

بررسی نقش در مرورگر فقط برای این است که به‌جای انبوه خطای دسترسی، یک پیام
قابل‌فهم ببینید.

### تغییرات کی روی سایت دیده می‌شوند؟

بلافاصله. صفحات ثابت‌اند ولی داده را در مرورگر هم از Supabase می‌گیرند، پس
ویرایش محصول نیازی به بیلد دوباره ندارد. فقط متن اولیهٔ HTML (که موتور جست‌وجو
می‌بیند) تا بیلد بعدی همان قبلی می‌ماند — برای تازه‌کردنش در تب `Actions` یک بار
`Run workflow` بزنید.

## معماری

### چرا سایت ثابت است ولی امن

روی GitHub Pages هیچ کد سمت سروری اجرا نمی‌شود. اگر مرورگر مستقیم در جدول
سفارش‌ها می‌نوشت، خریدار می‌توانست مبلغ را دست‌کاری کند.

راه‌حل: **خودِ دیتابیس نقش سرور را بازی می‌کند.** ثبت سفارش از تابع
`place_order` رد می‌شود — یک تابع `SECURITY DEFINER` در Postgres که:

- هر مبلغی را که مرورگر فرستاده باشد **نادیده می‌گیرد**
- قیمت، موجودی و وضعیت هر محصول را از جدول `products` می‌خواند
- ردیف محصول را قفل می‌کند تا دو سفارش هم‌زمان یک موجودی را دوبار نفروشند
- شماره موبایل، کد پستی و نشانی را دوباره اعتبارسنجی می‌کند
- رنگ انتخابی را با پالت واقعی محصول تطبیق می‌دهد
- مبلغ را خودش حساب می‌کند و موجودی را کم می‌کند

جدول `orders` هیچ سیاست خواندن یا نوشتن عمومی ندارد. تنها راه ورود سفارش،
همین تابع است.

### موتور اسکرول

هر ویژگی بصری یک **تابع محض از موقعیت اسکرول** است — نه state، نه trigger، نه
افکت یک‌باره. برای همین اسکرول به بالا خودبه‌خود همان انیمیشن را دقیقاً معکوس
اجرا می‌کند.

یک پنل `sticky` همان‌جا آزاد می‌شود که بخش بعدی شروع می‌شود، پس طبیعتاً هیچ
هم‌پوشانی زمانی‌ای نیست و crossfade ممکن نمی‌شود. هر پرده به‌جز اولی
`margin-top: -100dvh` دارد و **همین حاشیهٔ منفی، خودِ پنجرهٔ گذار است**.

⚠️ ارتفاع پردهٔ ۲ (`min-h-[300dvh]` در `app/page.tsx`) **ساختاری** است. یک صفحه
صرف گذار ورود می‌شود و یک صفحه صرف خروج؛ کمترش کنید، گرید قبل از ظاهرشدن کامل
شروع به محو‌شدن می‌کند.

### لایهٔ سقوط نرم

اگر کلید Supabase نباشد، همه‌چیز خودکار روی دادهٔ نمونه می‌افتد. خطای کوئری هم
به همان مسیر می‌رود تا اختلال گذرای دیتابیس صفحهٔ اصلی را سفید نکند.

## دربارهٔ پرداخت آنلاین

**پرداخت آنلاین در این نسخه وجود ندارد.** سفارش کامل ثبت می‌شود و در پنل
می‌بینیدش، ولی هماهنگی پرداخت با خودتان است (تماس، کارت‌به‌کارت، یا هر روشی که
ترجیح می‌دهید). چک‌اوت هم همین را صریح به مشتری می‌گوید.

دلیلش فنی است، نه سلیقه‌ای: تأیید تراکنش زرین‌پال به کد سمت سرور نیاز دارد،
چون کد پذیرنده باید مخفی بماند. روی GitHub Pages چنین جایی وجود ندارد.

اگر بعداً پرداخت آنلاین خواستید، سایت را روی یک هاست ایرانی (لیارا یا ابرآروان)
ببرید — آن‌وقت هم سرور دارید و هم IP ایران، که زرین‌پال به آن حساس است.

## جایگزینی دنبالهٔ عکس با فایل واقعی

پس‌زمینهٔ پرده‌های ۱ و ۳ الان **تولیدی** است — یک پیکرهٔ انتزاعی که همان‌جا روی
canvas کشیده می‌شود، چون هنوز عکسی آماده نیست و فایل تصویری نباید در مخزن گیت
باشد.

وقتی فریم‌های واقعی آماده شد، از پنل → **پرده‌ها** آپلودشان کنید:

- نام فایل‌ها را صفر‌دار و مرتب بگذارید: `frame-0001.webp` تا `frame-0096.webp`.
- پیشنهاد: ۹۶ فریم دسکتاپ، ۴۸ فریم موبایل (در `components/hero/HeroMotion.tsx`).
- یک پوستر هم آپلود کنید؛ قبل از آماده‌شدن فریم‌ها و در حالت کاهش حرکت دیده می‌شود.

⚠️ **حجم:** ۴۸ فریم WebP با کیفیت خوب حدود ۲ مگابایت می‌شود. اگر روی اینترنت
موبایل ایران سنگین بود: تعداد فریم را کم کنید، کیفیت را پایین بیاورید، یا به
ویدیوی لوپ برگردید — `FrameSource` طوری طراحی شده که این تعویض یک فایل است.

## راستی‌آزمایی

```bash
npm run build

# خروجی ثابت را دقیقاً مثل GitHub Pages، زیر یک زیرشاخه سرو کنید
mkdir -p /tmp/pages/web-site-makt && cp -r out/. /tmp/pages/web-site-makt/
python3 -m http.server 4300 --directory /tmp/pages

node scripts/verify-scroll.mjs http://127.0.0.1:4300/web-site-makt
node scripts/verify-flows.mjs  http://127.0.0.1:4300/web-site-makt
```

**`verify-scroll.mjs`** فقط اسکرین‌شات نمی‌گیرد. در چند نقطه به پایین اسکرول
می‌کند و شفافیت هر پرده را می‌خواند، بعد دقیقاً همان نقاط را به بالا می‌رود و
مقایسه می‌کند. هر افکت یک‌باره یا state پنهانی اینجا به‌صورت عدم تطابق ظاهر
می‌شود. هم‌چنین چک می‌کند هر سه پرده جایی به شفافیت کامل برسند و در حالت کاهش
حرکت هیچ پرده‌ای نیمه‌محو نباشد.

**`verify-flows.mjs`** مسیر خرید، اعتبارسنجی فرم (از جمله پذیرفته‌شدن ارقام
فارسی)، گیت پنل مدیریت و سطوح سئو را می‌گیرد.

اجرا زیر زیرشاخه مهم است: `basePath` اشتباه، خطایی است که فقط بعد از انتشار
واقعی خودش را نشان می‌دهد.

## محدودیت‌های شناخته‌شده

۱. **پرداخت آنلاین ندارد.** توضیح کامل در بخش بالا.

۲. **مسیر Supabase تست واقعی نشده.** کوئری‌ها، سیاست‌های RLS و تابع
`place_order` با دقت نوشته شده‌اند، ولی تا وقتی کلید وارد نشود اجرا نشده‌اند.
فایل‌های SQL طوری نوشته شده‌اند که یک‌باره و بدون خطا اجرا شوند.

۳. **متن HTML اولیه تا بیلد بعدی قدیمی می‌ماند.** بازدیدکننده همیشه دادهٔ تازه
می‌بیند (در مرورگر گرفته می‌شود)، ولی چیزی که موتور جست‌وجو می‌خواند مربوط به
آخرین بیلد است. برای تازه‌کردن، در `Actions` یک `Run workflow` بزنید.

۴. **فونت تیتر Estedad است، نه Morabba.** Morabba از هیچ منبع در دسترسی قابل
دریافت نبود. Estedad — که در طرح اولیه هم به‌عنوان جایگزین نام برده شده بود —
جای آن نشسته. اگر فایل‌های Morabba را دارید، تعویض فقط عوض‌کردن فایل در
`app/fonts/` و یک خط در `app/layout.tsx` است.
