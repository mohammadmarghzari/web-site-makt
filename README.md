# MAKT — فروشگاه اکشن‌فیگور

فروشگاه تک‌برند اکشن‌فیگورهای کلکسیونی مقیاس ۱/۱۲. فارسی، راست‌چین، با سه «پردهٔ» تمام‌صفحه که با اسکرول به‌صورت سینمایی و **کاملاً دوطرفه** به هم تبدیل می‌شوند.

**وضعیت: هر هفت فاز تمام شده.** سایت، پنل مدیریت، سبد خرید، چک‌اوت و درگاه پرداخت همه ساخته و تست شده‌اند.

سایت **همین حالا بدون هیچ تنظیماتی کار می‌کند** و روی دادهٔ نمونه بالا می‌آید. با وارد‌کردن کلیدهای Supabase به دادهٔ واقعی و پنل مدیریت سوییچ می‌کند، و با وارد‌کردن کد پذیرندهٔ زرین‌پال به پرداخت واقعی.

## ۱) دیپلوی روی Vercel از موبایل

همه‌چیز فقط با مرورگر موبایل و گیت‌هاب وب انجام می‌شود.

### الف) برنچ `main` آماده است

همهٔ کد روی برنچ **`main`** است و همان چیزی است که باید دیپلوی شود. برنچ
`claude/new-session-hsr652` هم دقیقاً همان کامیت‌ها را دارد و صرفاً برنچ کاری
است؛ می‌توانید بعداً پاکش کنید.

> اگر گیت‌هاب هنوز برنچ کاری را به‌عنوان پیش‌فرض نشان می‌دهد (چون اول آن پوش
> شده بود)، در `Settings` → `General` → `Default branch` آن را روی `main`
> بگذارید. برای دیپلوی الزامی نیست — در مرحلهٔ بعد برنچ را صریحاً انتخاب
> می‌کنید.

### ب) ایمپورت در Vercel

`vercel.com` → `Continue with GitHub` → `Add New…` → `Project` → مخزن `web-site-makt` → `Import`.

Vercel خودش Next.js را تشخیص می‌دهد. **هیچ تنظیمی را دست نزنید.**

مطمئن شوید برنچ پروداکشن روی `main` است:
`Settings` → `Git` → `Production Branch` → `main`.

### ج) Deploy

دکمهٔ `Deploy`. بعد از حدود یک دقیقه لینک `*.vercel.app` فعال است. **هر پوش بعدی خودکار دیپلوی می‌شود.**

در این مرحله سایت با دادهٔ نمونه کار می‌کند: سه پرده، کاتالوگ، صفحهٔ محصول، سبد خرید و چک‌اوت با پرداخت آزمایشی.

### د) دامنه (اختیاری)

`Settings` → `Domains` → دامنه را بنویسید → `Add`. رکوردهای DNS همان‌جا نشان داده می‌شوند؛ همان‌ها را در پنل ثبت‌کنندهٔ دامنه وارد کنید.

بعد از افزودن دامنه، متغیر `NEXT_PUBLIC_SITE_URL` را روی همان دامنه بگذارید — لینک بازگشت از درگاه پرداخت و آدرس‌های sitemap از روی آن ساخته می‌شوند.

## ۲) وصل‌کردن دیتابیس

بدون این مرحله سایت کار می‌کند ولی محصولات ثابت‌اند و پنل مدیریت غیرفعال است.

**۱.** در `supabase.com` یک پروژهٔ رایگان بسازید (کارت بانکی نمی‌خواهد).

**۲.** در داشبورد → `SQL Editor` → `New query` → کل محتوای فایل
`supabase/migrations/0001_init.sql` را پیست و `Run` کنید.

این فایل جدول‌ها، سیاست‌های امنیتی، باکت‌های فایل و ۶ محصول اولیه را می‌سازد. اجرای دوبارهٔ آن هم خطا نمی‌دهد و داده را پاک نمی‌کند.

**۳.** در داشبورد → `Project Settings` → `API` سه مقدار را بردارید و در Vercel →
`Settings` → `Environment Variables` وارد کنید:

| متغیر | از کجا |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon / public key |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role key |

⚠️ کلید `service_role` به همه‌چیز دسترسی کامل دارد. فقط در پنل Vercel واردش کنید — هرگز در کد، در پیام، یا در فایل `.env` کامیت‌شونده.

**۴.** در Vercel یک بار `Redeploy` بزنید.

**۵.** به `/admin/login` بروید، «اولین بار است؟ حساب بسازید» را بزنید و با ایمیل و رمز ثبت‌نام کنید.

**۶.** برگردید به SQL Editor و این خط را با ایمیل خودتان اجرا کنید:

```sql
update public.profiles set role = 'admin' where email = 'you@example.com';
```

ثبت‌نام به‌تنهایی دسترسی مدیر نمی‌دهد — این خط می‌دهد. پس لو‌رفتن آدرس `/admin` خطری ندارد.

**۷.** یک بار خارج و دوباره وارد شوید. پنل فعال است.

## ۳) فعال‌کردن پرداخت واقعی

تا وقتی کد پذیرنده نگذاشته‌اید، چک‌اوت با یک **درگاه آزمایشی داخلی** کار می‌کند: سفارش ثبت می‌شود، صفحهٔ پرداخت باز می‌شود، ولی هیچ پولی جابه‌جا نمی‌شود. صفحه هم صریحاً می‌گوید آزمایشی است.

برای پرداخت واقعی، در Vercel:

```
ZARINPAL_MERCHANT_ID = کد پذیرندهٔ شما
ZARINPAL_SANDBOX     = false
```

و `NEXT_PUBLIC_SITE_URL` باید دقیقاً دامنهٔ نهایی سایت باشد.

⚠️ **این را حتماً بخوانید:** سرورهای Vercel خارج از ایران هستند. اگر زرین‌پال درخواست را رد کرد، مشکل از کد نیست. چون کل پرداخت پشت لایهٔ `PaymentProvider` نوشته شده، مهاجرت به هاست ایرانی (لیارا یا ابرآروان) فقط تغییر محل دیپلوی است، نه بازنویسی کد.

## متغیرهای محیطی

| متغیر | لازم برای | توضیح |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | دیتابیس | آدرس پروژهٔ Supabase |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | دیتابیس | کلید عمومی — امن است، چون RLS جلوی سوءاستفاده را می‌گیرد |
| `SUPABASE_SERVICE_ROLE_KEY` | ثبت سفارش | **فقط سرور.** بدون آن سفارش‌ها ذخیرهٔ دائمی نمی‌شوند |
| `ZARINPAL_MERCHANT_ID` | پرداخت واقعی | فقط سرور |
| `ZARINPAL_SANDBOX` | پرداخت واقعی | تا وقتی کد پذیرنده ندارید `true` بماند |
| `NEXT_PUBLIC_SITE_URL` | پرداخت و سئو | دامنهٔ نهایی، مثل `https://makt.ir` |

هیچ‌کدام برای بالا‌آمدن سایت الزامی نیستند. نمونهٔ کامل در `.env.example`.

## پنل مدیریت

نشانی: `/admin` — راست‌چین، با همان پالت سایت، و **کاملاً قابل استفاده از موبایل**.

- **محصولات** — جست‌وجو، فیلتر وضعیت، افزودن و ویرایش، آپلود چند عکس، جابه‌جایی ترتیب، و حذف با تایپ نام محصول به‌عنوان تأیید.
- **پرده‌ها** — آپلود دسته‌ای فریم‌های دنبالهٔ عکس، آپلود پوستر، ویرایش خط‌به‌خط تیتر، اسلایدر شدت تیرگی، و **پیش‌نمایش زنده** که از همان موتور رندر واقعی استفاده می‌کند.
- **سفارش‌ها** — مشخصات مشتری، اقلام، مبلغ، وضعیت پرداخت و شمارهٔ پیگیری.
- **تنظیمات** — نام برند، لوگو، شبکه‌های اجتماعی، هزینهٔ ارسال.
- **خلاصه** — آمار، هشدار محصولات رو به اتمام، و هشدار تنظیمات ناقص (مثل فعال‌بودن درگاه آزمایشی).

امنیت سه لایه دارد: `proxy.ts` ورود را چک می‌کند، لایوت پنل نقش مدیر را چک می‌کند، و RLS در خود دیتابیس هر نوشتن غیرمجاز را رد می‌کند. لایهٔ سوم آن است که واقعاً از داده محافظت می‌کند؛ دو تای اول فقط پیام خطای قابل‌فهم می‌دهند.

## معماری

### لایهٔ سقوط نرم

`lib/repo/` بین کامپوننت‌ها و منبع داده نشسته. اگر کلید Supabase نباشد، خودکار دادهٔ نمونه برمی‌گرداند. خطای کوئری هم به همان مسیر می‌افتد تا یک اختلال گذرای دیتابیس صفحهٔ اصلی را سفید نکند.

`lib/types.ts` آینهٔ دقیق اسکیمای Postgres است، پس عوض‌شدن منبع داده هیچ کامپوننتی را دست نمی‌زند.

### موتور اسکرول

هر ویژگی بصری یک **تابع محض از موقعیت اسکرول** است — نه state، نه trigger، نه افکت یک‌باره. برای همین اسکرول به بالا خودبه‌خود همان انیمیشن را دقیقاً معکوس اجرا می‌کند.

یک پنل `sticky` همان‌جا آزاد می‌شود که بخش بعدی شروع می‌شود، پس طبیعتاً هیچ هم‌پوشانی زمانی‌ای وجود ندارد و crossfade ممکن نیست. هر پرده به‌جز اولی `margin-top: -100dvh` دارد و **همین حاشیهٔ منفی، خودِ پنجرهٔ گذار است**.

⚠️ ارتفاع پردهٔ ۲ (`min-h-[300dvh]` در `app/page.tsx`) **ساختاری** است. یک صفحه صرف گذار ورود می‌شود و یک صفحه صرف خروج؛ اگر کمترش کنید، گرید قبل از اینکه کامل ظاهر شود شروع به محو‌شدن می‌کند.

### امنیت پرداخت

مبلغ **همیشه** سمت سرور از دیتابیس دوباره حساب می‌شود (`lib/checkout/quote.ts`). از مرورگر فقط شناسهٔ محصول، رنگ و تعداد گرفته می‌شود. هیچ عددی دربارهٔ پول از کلاینت پذیرفته نمی‌شود.

`verify` ایدمپوتنت است: سفارشِ از قبل پرداخت‌شده زودتر برمی‌گردد، به‌روزرسانی مشروط به وضعیت `pending` است، و کد ۱۰۱ زرین‌پال («قبلاً تأیید شده») موفق حساب می‌شود. رفرش صفحهٔ بازگشت، سفارش را دوبار ثبت نمی‌کند.

## جایگزینی دنبالهٔ عکس با فایل واقعی

پس‌زمینهٔ پرده‌های ۱ و ۳ الان **تولیدی** است — یک پیکرهٔ انتزاعی که همان‌جا روی canvas کشیده می‌شود، چون هنوز عکسی آماده نیست و فایل تصویری نباید در مخزن گیت باشد.

وقتی فریم‌های واقعی آماده شد، از پنل → **پرده‌ها** آپلودشان کنید:

- نام فایل‌ها را صفر‌دار و مرتب بگذارید: `frame-0001.webp` تا `frame-0096.webp`. سیستم بر اساس نام مرتب می‌کند.
- پیشنهاد: ۹۶ فریم برای دسکتاپ، ۴۸ فریم برای موبایل (در `components/hero/HeroMotion.tsx`).
- یک تصویر پوستر هم آپلود کنید؛ قبل از آماده‌شدن فریم‌ها و در حالت کاهش حرکت نشان داده می‌شود.

به‌محض اینکه فریمی آپلود شود، سایت خودکار از فایل‌های واقعی استفاده می‌کند به‌جای تصویر تولیدی.

⚠️ **حجم:** ۴۸ فریم WebP با کیفیت خوب حدود ۲ مگابایت می‌شود. اگر روی اینترنت موبایل ایران سنگین بود: تعداد فریم را کم کنید، کیفیت WebP را پایین بیاورید، یا به ویدیوی لوپ برگردید — `FrameSource` طوری طراحی شده که این تعویض یک فایل است.

## راستی‌آزمایی

```bash
npm run build
NEXT_PUBLIC_SITE_URL=http://127.0.0.1:3000 npm start   # ترمینال جدا

node scripts/verify-scroll.mjs   # موتور اسکرول
node scripts/verify-flows.mjs    # سبد، چک‌اوت، پرداخت، پنل، سئو
```

**`verify-scroll.mjs`** فقط اسکرین‌شات نمی‌گیرد. در چند نقطه به پایین اسکرول می‌کند و شفافیت هر پرده را می‌خواند، بعد دقیقاً همان نقاط را به بالا می‌رود و مقایسه می‌کند. هر افکت یک‌باره یا state پنهانی اینجا به‌صورت عدم تطابق ظاهر می‌شود. هم‌چنین چک می‌کند هر سه پرده جایی به شفافیت کامل برسند و در حالت کاهش حرکت هیچ پرده‌ای نیمه‌محو نباشد.

**`verify-flows.mjs`** مسیر واقعی خرید را می‌رود و دو چیز را که با چشم دیده نمی‌شوند تست می‌کند: رد‌شدن شمارهٔ موبایل و کد پستی نامعتبر (و پذیرفته‌شدن ارقام فارسی)، و **ایدمپوتنت‌بودن بازگشت از درگاه** — یعنی رفرش و replay صفحهٔ بازگشت نباید سفارش را دوبار ثبت کند.

خروجی: اسکرین‌شات‌ها در `.verify/` (در گیت نادیده گرفته می‌شود) و گزارش PASS/FAIL.

## محدودیت‌های شناخته‌شده

۱. **تماس واقعی با زرین‌پال تست نشده.** از محیط توسعه اتصال به `payment.zarinpal.com` برقرار نمی‌شود. کد دقیقاً طبق قرارداد مستند نوشته شده (نسخهٔ v4، ارسال صریح `currency: "IRT"`، پذیرش کد ۱۰۱ به‌عنوان موفق) و کل جریان با درگاه ساختگی تست شده — ولی اولین تراکنش واقعی را خودتان باید تأیید کنید.

۲. **مسیر Supabase تست واقعی نشده.** کوئری‌ها و سیاست‌های RLS با دقت نوشته شده‌اند، ولی تا وقتی کلید وارد نشود اجرا نشده‌اند. فایل SQL طوری نوشته شده که یک‌باره و بدون خطا اجرا شود.

۳. **بدون `SUPABASE_SERVICE_ROLE_KEY`، سفارش‌ها فقط در حافظهٔ سرور می‌مانند** و با هر ری‌استارت پاک می‌شوند. پنل مدیریت خودش این را هشدار می‌دهد.

۴. **فونت تیتر Estedad است، نه Morabba.** Morabba از هیچ منبع در دسترسی قابل دریافت نبود. Estedad — که در طرح اولیه هم به‌عنوان جایگزین نام برده شده بود — جای آن نشسته. اگر فایل‌های Morabba را دارید، تعویض فقط عوض‌کردن فایل در `app/fonts/` و یک خط در `app/layout.tsx` است.
